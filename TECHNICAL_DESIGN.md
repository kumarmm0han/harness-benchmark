# Technical design

## DES-001 — Runtime and schema
References: ARC-001, ARC-003; PRN-003, PRN-006, PRN-007; DR-001, DR-003, NFR-001.
Backend package `demo.sop` uses Spring Web, JDBC, Flyway, PostgreSQL and SnakeYAML. Flyway creates drafts (ID, original source, revision, failed revision, current version) and publications (ID, version, draft revision, source, JSONB snapshot). A composite foreign key enforces the current pointer. Publications reject UPDATE/DELETE through a database trigger. PostgreSQL row locking coordinates save/publish; insertion uses ON CONFLICT for concurrent first saves. Demo profile inserts a classpath template with ON CONFLICT DO NOTHING. Compose uses PostgreSQL 17, Java 21 and Node 22 build images; frontend runtime serves static assets and proxies /api to backend. Health checks and service_healthy dependencies replace startup sleeps.

## DES-002 — Compiler
References: ARC-002; PRN-001, PRN-004, PRN-005; FR-020, FR-021, FR-030, FR-032, FR-034, NFR-020.
`Compiler` exposes a result containing valid, issues and content. A line parser requires the exact front matter and seven sections, each once. Prose permits nonempty bullet lines only; each machine section contains one yaml fence only. SnakeYAML SafeConstructor with duplicate-key rejection and explicit node traversal enforces standard scalar/map/sequence tags, no alias events, finite numbers and maximum collection depth 20. YAML implicit scalars remain typed; schema validation performs no coercion. Object allowlists reject unknown fields. Structural checks accumulate field issues; semantic checks validate unique IDs, references, condition compatibility, intent restrictions and the centralized refund limit/escalation invariant. Issues sort by path then code. No source executes. Missing refund limit and matching escalation are separate semantic errors even if both are absent. Content exists only when no issues remain.

## DES-003 — API and transactions
References: ARC-003, ARC-004; PRN-004, PRN-006; FR-001, FR-010, FR-042, FR-043, FR-045, FR-050, IR-001.
`Api` maps the eight specified operations under /api/v1; DTO records reject unknown JSON properties and require exact source/revision types. `IdentityFilter` enforces identity/roles and configured local-origin CORS. `Errors` translates exceptions to {code,message,issues}. `Store` uses JdbcTemplate and TransactionTemplate: lock draft, check revision/duplicate, compile saved source and ID, then either persist failure and return a rejection result after commit or insert next version and update pointer atomically. Save clears failure and increments revision without altering current content. Versions start at 1 and increment only on success. Current reads join the pointer to the immutable snapshot; history is author-only. Invalid filter values yield 400; all lists order by sop_id. Source over 65536 UTF-8 bytes yields 413 before persistence. Unexpected failures produce generic 500 responses. No request content is logged.

## DES-004 — React UI
References: ARC-005; PRN-001, PRN-004; FR-010, FR-034, FR-045, FR-050, FR-052, FR-053, NFR-050.
A small App and typed API helper manage the identity, published filters/list, author draft list/editor, validation and selected snapshot. Accessible native controls use labels and status/alert text. Identity changes reset author state. Network responses are checked before state replacement. Saved source is tracked separately to disable publication of unsaved edits. Human detail explicitly renders every canonical field; JSON view stringifies the identical snapshot object. No raw HTML rendering. The template is generated from the frozen spec into the shared seed and frontend asset with an equality check. No routing library or global state framework is needed for four simple screen areas.

## DES-005 — Verification
References: ARC-006; PRN-008, PRN-009; NFR-041; all acceptance journeys.
`make verify` runs Maven build/unit and PostgreSQL integration tests, frontend Vitest/Testing Library tests, TypeScript checks, ESLint and Vite production build. Integration tests connect to a disposable PostgreSQL container supplied by the verification script (never H2). `make demo` builds/starts Compose with readiness checks. `make smoke` uses Python standard-library HTTP calls against Compose, covers publication, financial failures, consumer permissions, invalid replacement/history and restart persistence; unique SOP IDs keep reruns safe. Tests also check direct malformed requests, source safety and version conflicts. README documents tools, API shapes, demo steps, restart/shutdown and explicit volume deletion. VERIFICATION.md records actual commands, coverage, assumptions and limitations.

## Assumptions
The source parser accepts CRLF without altering stored bytes, and '- ' / '* ' as plain bullets. Save path IDs use the SOP identifier syntax even when content is incomplete. Failed-publication indicator is a nullable `failed_revision` (draft summaries also expose current_version so the UI can report retained availability). Financial missing-limit issues are semantic, allowing independent discovery of missing escalation. Only API paths require demo identity; service health is public for Compose readiness. No requirements are deferred.

Acceptance mapping: AC-E2E-001 template/save/publish/filter; AC-E2E-002 independent safety errors and correction; AC-E2E-003 identical consumer views and denied mutation; AC-E2E-004 invalid replacement and preserved history; AC-E2E-005 clean startup and restart persistence.
